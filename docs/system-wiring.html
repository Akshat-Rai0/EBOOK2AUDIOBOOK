Data contract

segment: { "id": "c03-p012-s2", "chapter": 3, "speaker": "Mira",
           "kind": "dialogue|narration|thought", "text": "...", "status": "pending|done" }
character: { "name": "Mira", "aliases": ["Ms. Vane"], "voice": {"engine": "xtts", "id": "..."} }

Storage

One project folder per book: book.json, segments.json, cast.json, audio/, state.sqlite (stage status per chunk, for resume).

Engine adapter

Every TTS engine implements one interface: synthesize(text, voice) -> wav, list_voices(), max_chars. New engines later mean a new adapter only.

Caveats to design around

  • Memory: load LLM, finish stage 3, unload, then load TTS.
  • Context limits: a small model cannot hold a chapter. Chunk and pass the running cast list; recheck alias merges in stage 4.
  • Engine text limits: XTTS-class models cap characters per call, so split at sentence edges.
  • Voice drift: fix the voice per character in cast.json; never re-pick at synthesis time.
  • Speed: a full novel is many hours of CPU synthesis. Show ETA and support pause and resume.
